# Раздача VPN на подключённые устройства без root

Документ фиксирует, почему прозрачной раздачи без root не существует, что вместо неё
сделано в Nova и что именно проверено на живых устройствах. Дата: 3 августа 2026.

## Почему нельзя просто завернуть трафик клиентов в туннель

`VpnService` заворачивает в tun трафик **по UID приложения**. У пакета, который телефон
форвардит от клиента точки доступа, UID нет вообще: он не порождён локальным сокетом.

Это видно в таблице правил маршрутизации любого устройства — вот Redmi Pad 2 Pro:

```
15040: from all fwmark 0x10064/0x1ffff iif lo uidrange 10153-10153 lookup 1015
16000: from all fwmark 0x10064/0x1ffff iif lo                      lookup 1015
17000: from all                        iif lo oif wlan0            lookup 1015
```

Каждое правило содержит `iif lo` — «только для трафика, порождённого на этом хосте».
Форвардинг приходит с `wlan1`/`rndis0` и не совпадает ни с одним из них, поэтому уходит
в основную таблицу, мимо tun. Добавить своё правило можно только через `ip rule` или
`iptables`, то есть через netd, то есть с root.

Обходных путей нет и рядом: интерфейс раздачи приложению не отдаётся, DNS-порт 53 на нём
занят системным резолвером и всё равно ниже 1024 (нужен `CAP_NET_BIND_SERVICE`),
DHCP-опции раздачи не настраиваются.

**Проверено экспериментом.** тестовое устройство с живым WARP раздаёт Wi-Fi, к нему подключён
планшет. Внешний IP планшета без настройки прокси — `178.34.161.39`, то есть обычный
адрес провайдера, а не выход туннеля `104.28.x.x`. Трафик клиента идёт мимо VPN.

Так же считает и остальной мир: `Mygod/VPNHotspot` (6245 звёзд) прямо пишет в описании
«root required», а запрос «No root?» закрыт как *wontfix*. Без root делают либо прокси на
телефоне (`YTwsy/pixel-proxy-gateway`, «Allow LAN» в v2rayNG, NekoBox, Clash), либо
приложение-клиент на той стороне (`nestchao/Hotspot-Bypass-VPN-Unlimited-Hotspot`).

## Что сделано

Nova работает шлюзом: слушает HTTP, HTTPS CONNECT и SOCKS5 на адресе раздачи, а исходящие
сокеты прокси — это сокеты самой Nova, поэтому они идут в туннель на общих основаниях.
Клиент один раз прописывает прокси у себя в настройках.

| Файл | Роль |
| --- | --- |
| `app/src/main/java/com/example/nova/GatewayEndpoints.kt` | находит интерфейсы раздачи |
| `app/src/main/java/com/example/nova/GatewayPortal.kt` | страница настройки и PAC-файл |
| `app/src/main/java/com/example/nova/LocalAppProxyManager.kt` | сам прокси, слушает на найденных адресах |
| `app/src/main/java/com/example/nova/LocalProxyActivity.kt` | экран «Раздача через Nova» |

### Как находится интерфейс раздачи

Точку доступа нельзя получить обычным способом, но и наивное «чего нет в
ConnectivityManager, то и есть раздача» неверно — **это была первая ошибка**. На Redmi Pad
2 Pro USB-модем виден системе как обычная сеть с интерфейсом `rndis0`, и такой фильтр
записывал его в аплинки: ровно тот интерфейс, ради которого всё затевалось, молча
выпадал.

Верный признак — отсутствие `NET_CAPABILITY_INTERNET`. Сторона раздачи никуда не ведёт,
она только принимает клиентов, поэтому этой способности у неё нет. Аплинки (Wi-Fi,
сотовая связь, VPN) её имеют всегда.

Дополнительно отсекаются служебные интерфейсы по имени. Важнее всего `v4-*` и `clat*`:
464XLAT поднимает IPv4-адрес из 192.0.0.0/29 поверх сотового IPv6 и легко сходит за
раздачу.

Подсети **не** захардкожены, и это оказалось принципиально: классических 192.168.43.1 и
192.168.42.129 не было ни разу. Реальные значения — `10.22.133.108` (USB-модем на Redmi)
и `192.168.217.114` (точка доступа на телефоне).

Если интерфейсов раздачи не нашлось, в лог пишется построчный разбор всего, что видит
приложение, с вердиктом по каждому интерфейсу — без этого разбирать жалобу «раздача не
появилась» на чужой прошивке невозможно.

### Портал и пароль

На отдельном порту 1371 поднимается страница с параметрами подключения и пошаговой
инструкцией, плюс PAC-файл. PAC вызывает `isInNet` только для литеральных IP: для имени
эта функция сначала сделала бы DNS-запрос, синхронно, на каждый URL в клиенте.

Логин и пароль страница показывает **только клиенту, пришедшему через раздачу**. Решает
не адрес отправителя (его подделывают), а адрес, на котором принято соединение:
подключение, принятое на интерфейсе раздачи, физически не может прийти из чужой сети.

Отдельно есть режим «без пароля для клиентов раздачи» — по умолчанию выключен. Он нужен
телевизорам и приставкам, где в настройках прокси попросту нет полей логина и пароля.
Действует по тому же правилу: только на интерфейсе раздачи, никогда — в общей сети.

## Что проверено на устройствах

Стенд: тестовое устройство (Android 14) раздаёт Wi-Fi и держит WARP, Redmi Pad 2 Pro (HyperOS 3)
подключён к этой точке доступа как обычный клиент со своим выключенным VPN.

| Проверка | Результат |
| --- | --- |
| Клиент без прокси | `178.34.161.39` — мимо VPN, как и предсказано |
| Клиент через HTTP CONNECT | `104.28.198.244` — выход WARP |
| Клиент через SOCKS5 | `104.28.198.244` |
| Клиент через обычный HTTP | `104.28.230.246` |
| Портал для клиента раздачи | отдал логин и пароль |
| Портал для клиента общей сети | пароль скрыт, отправляет в приложение |
| Прокси без пароля | 407 |
| Без пароля + режим для раздачи, интерфейс раздачи | работает |
| Без пароля + режим для раздачи, общая сеть | 407 |
| Без пароля + режим для раздачи, loopback | 407 |

Обнаружение интерфейсов проверено на трёх типах: точка доступа Wi-Fi (`wlan1`, телефон),
USB-модем (`rndis0`, Redmi) и общая сеть Wi-Fi (`wlan0`, оба устройства).

## Найдено попутно

**Настройки не доходили до службы.** `NovaVpnService` живёт в процессе `:vpn`, а экран —
в основном. SharedPreferences в `MODE_PRIVATE` кешируются каждым процессом независимо и
не перечитываются, поэтому служба не видела включения раздачи до полного перезапуска
приложения. Флаги и учётные данные продублированы в `gateway_flags.json` — файл читается
заново каждый раз. Проверено: переключатель теперь действует сразу, портал поднимается и
гаснет вслед за ним.

**Экран дёргал службу на каждом кадре.** Перерисовка идёт раз в 900 мс, и запрос
пересинхронизации уходил на каждой. За несколько минут с открытым экраном при лежащем VPN
набежало больше двухсот запусков службы. Теперь не чаще раза в три секунды.

## Туннель не переживал смену сети

Это нашлось при проверке раздачи и оказалось не про раздачу вовсе. После перехода
Wi-Fi → LTE Nova писала в лог «tunnel-probe через текущий VPN уже проходит, реконнект не
требуется», хотя через туннель уже не проходило ни байта.

Проверка здоровья принимала **накопленные** доказательства вместо живых:

- `substantialTraffic` в `observeImportedExactAwgTrafficProof` смотрит на счётчики за всё
  время жизни туннеля;
- рукопожатие считается свежим целых три минуты;
- `hasRecentConfirmedWarpExitSnapshot` отдаёт снимок выхода возрастом до шести секунд.

После переезда сокета на другой интерфейс все три условия ещё выполняются — и мёртвый
туннель объявлялся живым.

Механизм для этого в коде уже был: `requiresFreshTunnelProbeNow()`, и смена подложной
сети исправно взводит его на 12–16 секунд. Просто пять мест его не спрашивали. Теперь
спрашивают — пока окно активно, засчитывается только живая проба.

Проверено на тестовом устройстве, шесть переключений Wi-Fi ↔ LTE подряд: туннель каждый раз
переезжает и остаётся рабочим, внешний IP меняется. До правки он умирал на первом же
переключении и сам не поднимался.

## Попутно: утечка tun-интерфейсов

Дескриптор дублировался дважды — в Kotlin через `dup().detachFd()` и ещё раз внутри Go в
`CreateAndroidTUN`. Go закрывает только свою копию, а у отсоединённой в Java владельца уже
нет, поэтому её не закрывал никто. Пока хоть один дескриптор открыт, интерфейс живёт:
после четырёх реконнектов на устройстве висели `tun0`..`tun3` одновременно.

Движку теперь отдаётся обычный fd без передачи владения — дублирование на его стороне
синхронное и происходит до возврата из `startVPN`. После шести переключений сети интерфейс
ровно один.

## Шлюз не зависит от состояния VPN

Раньше прокси поднимался только при живом туннеле и гас вместе с ним. Для клиента это
выглядело не как «VPN отключился», а как «интернет пропал», и он шёл перенастраивать
телевизор. Теперь слушающие сокеты живут, пока раздача включена, а решение «выпускать или
нет» принимается на каждом подключении.

Когда туннеля нет, трафик **не выпускается**: клиент подключился к раздаче ради VPN, и
молча выпустить его напрямую — это не «связь продолжила работать», а незаметная утечка.
Вместо этого HTTP получает 503 с объяснением по-русски, а SOCKS5 — код 0x02 (запрещено
политикой). Настроить клиента можно заранее, до подключения VPN: как только туннель
поднимется, всё заработает само. Для тех, кому нужна связь любой ценой, есть отдельный
переключатель «Без VPN выпускать напрямую», по умолчанию выключенный.

Служба остаётся в foreground, даже когда VPN остановлен, — но только пока раздача
включена. Без foreground Android быстро убил бы её, и шлюз исчез бы тем же способом,
только с задержкой. Как только раздачу выключают, служба останавливается.

Проверено на тестовом устройстве: раздача включается при выключенном VPN (портал 200, прокси 503),
переживает остановку туннеля и сама возобновляет проход после переподключения;
выключение раздачи закрывает оба порта и останавливает службу.

## Можно ли отдать клиентам свой DNS

Короткий ответ: для трафика, идущего через прокси, — **это уже работает**; для остального
без root нельзя.

Имена сайтов, которые клиент открывает через прокси, разрешает сам телефон: и HTTP
CONNECT, и SOCKS5 с удалённым разрешением имён передают имя целиком. Дальше запрос
попадает в туннель, где его перехватывает Go-ядро по политике из настроек Nova
(`Nova.setDnsInterceptPolicy`). То есть правила DNS распространяются на клиентов
автоматически, настраивать у них ничего не нужно.

Отдать клиентам телефон как DNS-сервер невозможно по двум независимым причинам. Порт 53
привилегированный: на обоих проверенных устройствах `ip_unprivileged_port_start` равен
1024, а у приложений нет `CAP_NET_BIND_SERVICE`. И даже будь он доступен, на интерфейсе
раздачи порт 53 уже занят системным DNS-форвардером Android, а адрес выдаёт его же
DHCP — ни то, ни другое без root не настраивается.

Отсюда практический совет, вынесенный на страницу портала: если в клиенте есть выбор
между `socks5` и `socks5h`, брать `socks5h`. Обычный `socks5` сначала разрешает имя у
себя и только потом идёт через прокси — то есть DNS утекает мимо.

Побочная находка: `LocalDnsProxyManager` занимает `127.0.0.1:53` и в текущей сборке
**никогда не запускается** — в `NovaVpnService` есть только вызовы `stop`. Если его
когда-нибудь подключат, он упрётся ровно в это ограничение.

## Что осталось

**Чего шлюз не умеет и не будет.** Через прокси идёт только TCP: браузеры, приложения,
стриминг. UDP — онлайн-игры, звонки, WebRTC — прокси не переносит, такой трафик пойдёт
мимо VPN. Системный DNS клиента тоже остаётся своим: через туннель разрешаются только
имена, которые запрашивает сам прокси. Полностью прозрачным для клиента это станет только
если Nova научится поднимать на интерфейсе раздачи AmneziaWG-сервер — тогда клиенту
хватит одного импортированного конфига, но и клиент должен уметь WireGuard.
