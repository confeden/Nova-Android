# Поддержка VLESS + REALITY в Nova

Документ фиксирует решения и измерения, на которых они основаны. Дата: 3 августа 2026.

## Итог в одну строку

VLESS + REALITY + Vision реализуются **внутри существующего Go-ядра `nova-core`**, а не
через встраивание Xray-core или sing-box. Разница измерена на этой машине: +307 КиБ
(или +1.12 МиБ вместе с uTLS для Vision) против +29.6 МиБ у Xray-core на каждую ABI.

## Почему не готовое ядро

| Вариант | Размер `libgojni.so` (arm64) | Вердикт |
| --- | --- | --- |
| `nova-core` сейчас | 21.7 МБ | базовая точка |
| `nova-core` + VLESS/REALITY/Vision/SOCKS5 | +307 КиБ … +1.12 МиБ | **выбрано** |
| + Xray-core (`distro/all`) | +29.6 МиБ | ×4 ABI ≈ +120 МБ к APK |
| + sing-box libbox | +27.4 МиБ | к тому же GPL-3.0 и **нет XHTTP** |

Ручная обрезка списка импортов Xray не помогает: `infra/conf/serial` тянет реестр всех
протоколов, и проба сэкономила лишь 200 КБ.

Дополнительно: **две gomobile-библиотеки в одном APK несовместимы** — каждая приносит
свой `libgojni.so` и `go.Seq`, символы конфликтуют. Поэтому «просто добавить
libv2ray.aar рядом» нельзя; либо всё в одном Go-модуле, либо C-shared `.so` (libXray,
MIT) с тонким JNI-слоем.

### Что берём из Xray-core (MPL-2.0, совместима с закрытым приложением)

- `transport/internet/reality` — клиентская часть REALITY, 299 строк; серверный пакет
  `github.com/xtls/reality` не нужен вовсе.
- `proxy/vless/encoding` — XTLS Vision.
- `transport/internet/splithttp` — XHTTP (~1500 строк). **Единственная функция, которой
  нет в sing-box и не будет.** В реальной подписке это 165 из 562 профилей, то есть
  без неё «полноценной поддержки» не выйдет.

Слияние Xray в `nova-core` сейчас невозможно из-за конфликта зависимостей: он тянет
`apernet/quic-go` → `qpack v0.6.0`, что ломает `quic-go v0.55.0`, а апгрейд до v0.61.0
ломает `Diniboy1123/connect-ip-go`. Поэтому — портирование нужных пакетов, не импорт.

## Как это встраивается в приложение

Существующая связка сохраняется: Go-ядро поднимает **SOCKS5-inbound на 127.0.0.1**, а
TUN прокачивается уже имеющимся `tun2proxy` (`app/src/main/cpp/native-lib.cpp:100`,
`tun2proxy_with_fd_run`). Защита сокетов от петли — через существующий
`nova.SetSocketProtector` / `novaengine.GlobalProtector`.

Устаревший `protect_path` (Unix-сокет с передачей fd) не нужен: в v2rayNG его больше
нет, в Xray-core 26.x хука protect тоже нет — достаточно
`Builder.addDisallowedApplication(packageName)`.

### Ловушки, найденные на реальных данных

- **`type=raw` — это `tcp`.** Xray переименовал транспорт; в списке так у 325 профилей.
  Клиент, знающий только `tcp`, отбрасывает больше половины подписки.
- **`fp=qq`, `fp=android`, `fp=360` ломают REALITY**: эти профили uTLS умеют только
  TLS 1.2, а REALITY требует TLS 1.3. В списке `fp=qq` у 111 профилей. Значение
  подменяется на `chrome` (см. `effectiveFingerprint`).
- **Имя узла (`#fragment`) нельзя включать в ключ сравнения.** Провайдер перенумеровывает
  узлы при каждой публикации: одно реальное изменение выглядело бы как 531 удаление и
  531 добавление, и вся пользовательская статистика обнулялась бы.
- **Ключ по `uuid+host+port` тоже неверен** — схлопывает 562 профиля в 388, потому что
  соседние строки отличаются только `fp` или `alpn`. Нужен полный набор параметров.
- **`extra=null`** встречается буквально строкой `null` (47 профилей) — не должно влиять
  ни на разбор, ни на identity.
- **Часы устройства**: REALITY кладёт unix-время в `SessionId[4:8]`, и сервер отвергает
  подключение при большом расхождении. При ошибке стоит проверять сдвиг часов и
  подсказывать пользователю.

Стенд: из вендоренных исходников собран обычный бинарник Xray под `android/arm64`

проверялся именно генератор конфигураций.

| Источник конфигурации | Результат |
| --- | --- |
| Готовые JSON из подписки (эталон) | **20 из 21** |
| Сгенерированные `VlessXrayConfig` из тех же узлов | **20 из 21** |

Совпадение поузловое: единственный неработающий узел (`94.183.170.95`) не отвечает и на
эталонной конфигурации, то есть лежит сам. Транспорт у всех — XHTTP поверх REALITY с
`mode=stream-up`, `path=/xh` и `xPaddingBytes`.

Это закрывает главный открытый вопрос: **связка «разбор ссылки → генерация конфигурации →
живое соединение» работает**, причём на сети с активной фильтрацией.

### Контрольная проверка, которая едва не увела в сторону

Первый прогон дал 0 из 21, и это выглядело как баг генератора. Причина оказалась в
тестовой оснастке: конвертер, собиравший `vless://` из JSON подписки, не переносил `path`
и `mode`. Nova честно сгенерировала то, что было в ссылке — `path=/`, `mode=auto` вместо
`/xh` и `stream-up`, — и сервер такие соединения не принимал. После починки конвертера
всё сошлось. Полезный побочный вывод: ссылка без параметров транспорта бесполезна, и
подписки, раздающие готовый JSON, нельзя упрощать до `vless://` «по основным полям».

### Публичный бесплатный список — отдельная история

Выборка из 27 узлов `BLACK_VLESS_RUS_mobile.txt` (все пять транспортов: tcp, ws, xhttp,
grpc, httpupgrade) дала 0 работающих. Это не генератор: TCP доходит до 26 из 27 узлов,
а сгенерированный JSON поэлементно совпадает с параметрами ссылки. У бесплатных публичных
списков ключи ротируются постоянно, и протухшие записи — норма. Вывод для приложения:
профили нужно проверять живой пробой, а не доверять факту разбора.

## Транспорт подключён к сервису

5 августа 2026. `NovaVpnService.runVlessPhase` поднимает ядро Xray, заворачивает TUN
через `tun2proxy` на `socks5://127.0.0.1:<порт>` и при любом отказе уходит в общую
цепочку WARP/AWG. Выбирается явно: регион `vless` плюс сохранённая ссылка профиля.

### Мина: два рантайма Go в одном процессе

Первый запуск на тестовом устройстве уронил процесс службы:

```
fatal error: unknown caller pc
runtime.copystack
goroutine 18 [copystack, locked to thread]:
encoding/json.typeFields
github.com/xtls/xray-core/infra/conf/serial.LoadJSONConfig
```

В процессе живут два независимых рантайма Go — `libgojni.so` от nova-core и
`libnovaxray.so`. Каждый при входе через cgo помечает поток своей структурой, и слот у
них общий. Поток подключения успевает вызвать `Nova.setSocketProtector` до VLESS, то
есть приходит в ядро Xray уже помеченным чужим рантаймом; при первом же росте стека —
на разборе конфигурации — размотчик уходит в кадры, которые ему не принадлежат.

Лечится разделением: все вызовы `XrayBridge` идут с единственного выделенного потока,
который в nova-core не заходит никогда. После этого ядро поднимается, конфигурация
разбирается, `tun2proxy` отдаёт соединения в SOCKS5, и Xray принимает их на
`socks-in >> proxy`.

Это же объясняет, почему `XrayBridge.version()` работал и раньше: он не растит стек.

### Мина: проба через сеть VPN не видит собственный туннель

Дальше туннель поднимался, но проба не проходила ни разу и фаза срывалась по таймауту.
Причина: при раздельном туннелировании «только выбранные приложения» пакет Nova
остаётся вне VPN, а приложение снаружи VPN своей же сети VPN не видит —
`findCurrentVpnNetwork` отдаёт null, и `hasTunnelConnectivity` вместе с ним всегда
false. У Opera ту же дыру закрывает прямая проверка HTTP-прокси
(`hasOperaProxyConnectivity`); для VLESS понадобился её аналог через SOCKS5.

## Живое подключение через приложение подтверждено

5 августа 2026, тестовое устройство, узел из публичной подписки `igareck/vpn-configs-for-russia`
(`BLACK_VLESS_RUS.txt`, 202 профиля).

Отбор узлов: `tools/probe_vless_live.sh` поднимает на устройстве обычный бинарник Xray с

публичных списков.

Затем рабочий узел подключён через приложение: `VLESS активен` за две секунды, а запрос
через socks-инбаунд ядра внутри приложения вышел с адреса узла, а не устройства
(145.241.174.111 против 178.34.161.39). То есть трафик действительно идёт через VLESS.

## Перебор профилей идёт сам

6 августа 2026. Мёртвый узел больше не останавливает подключение: `runVlessPhase`
идёт по списку от активной записи, а неудачную уводит вниз хранилища
(`ClientData.demoteVlessProfileLink`). Порядок и наказание вынесены в чистый
`ProfileRotation` — его проверяют обычные unit-тесты, а не устройство.

Ключевое решение: **порт SOCKS выбирается один раз на всю фазу**. Смена профиля
перезапускает только ядро Xray, TUN и tun2proxy остаются на месте. Поэтому после
первого живого узла перебор не рвёт системный VPN, а мёртвые кандидаты вообще не
доходят до `establish`: они отсеиваются пробой SOCKS-инбаунда до подъёма интерфейса.

Измерено на тестовом устройстве, публичная подписка на 151 профиль: мёртвый узел стоит
~4.2 с, живой находится за 35–47 с. Второй запуск дошёл до того же рабочего узла
за 9 попыток вместо 12 — наказание сработало.

### Мина: REAPPLY на живом VLESS роняет процесс службы

Кнопка «следующий профиль» сначала отправляла `ACTION_REAPPLY_CURRENT_SESSION`.
Пересборка сессии останавливает tun2proxy, и его рабочий поток при завершении зовёт
`exit()`, а тот падает в `__cxa_finalize`:

```
Fatal signal 11 (SIGSEGV) in tid 26208 (Thread-131), pid (.brent.nova:vpn)
  #01 libc.so (__cxa_finalize+144)
  #02 libc.so (exit+24)
  #03 libtun2proxy.so
```

Процесс :vpn умирал, ActivityManager планировал перезапуск через четыре минуты, и
фактически сеть возвращалась через 77 секунд — по фоновому heartbeat. Лечится тем же
приёмом, что и авто-перебор: `ACTION_SWITCH_VLESS_PROFILE` меняет узел на ходу,
tun2proxy не трогают вовсе, и опасного участка просто нет.

### Мина: `SharedPreferences` не бывают межпроцессными

Кнопка «следующий профиль» после успешного подключения возвращала перебор к уже
отвергнутым узлам, а счётчик начинался заново с «1/151». Причина не в переборе:
служба живёт в процессе `:vpn`, а `SharedPreferences` каждый процесс держит своей
копией в памяти и чужих записей не видит. Экран считал «следующий» по списку на
момент своего запуска — то есть по порядку до всех перестановок.

Лечится двумя правками, и обе нужны:

- список профилей и активная ссылка переехали из prefs в `vless_profiles.json`
  (`AtomicFile`, читается заново при каждом обращении). Формат прежний, старая
  установка переносится один раз при первом чтении;
- какой профиль следующий, решает служба, а не экран. `ACTION_SWITCH_VLESS_PROFILE`
  идёт без параметров: у экрана нет данных, чтобы выбрать правильно.

### Номер профиля — это место в списке

Счётчик считает не попытки, а позицию записи, и из этого следуют два правила.

Наказание откладывается до конца прохода. Если уводить запись вниз сразу, следующая
занимает её место, текущий профиль всегда остаётся первым, и счётчик застревает на
«1/151». Отвергнутые уезжают вниз одной пачкой в момент успеха.

Удачный профиль поднимается в начало списка. Иначе рабочий узел остаётся там, где
его застал перебор (например, шестым), над ним лежат непроверенные записи, и
«следующий профиль» уводит не вниз от рабочего, а в непроверенную часть списка.

Итог на устройстве: рабочий профиль показывается «1/151», нажатие «следующий» сразу
даёт «2/151», а отвергнутые в этом круге больше не пробуются.

## Пинг при VLESS

Экран измерить задержку не может по той же причине, по которой не работала проба
туннеля: при раздельном туннелировании он снаружи VPN, а порт SOCKS-инбаунда ядра
служба выбирает на лету и никому не сообщает. Поэтому замер делает сама служба —
даром, она и так проверяет узел раз в полторы секунды, остаётся засечь длительность
пробы. Результат публикуется в `transport_latency.json`, экран его читает и рисует
обычным графиком. На тестовое устройство живой узел даёт 180–240 мс.

## DNS уходил мимо туннеля целиком

6 августа 2026, тестовое устройство. Первая проверка сняла подозрение с самого DNS:
`tools/probe_vless_dns.py` через SOCKS-инбаунд ядра дал 36 успешных запросов из 36
(1.1.1.1, 1.0.0.1, 8.8.8.8), 97–135 мс. Режим `OverTcp` у tun2proxy работает.

Дефект нашёлся в логе tun2proxy: **DNS-сессий там не было вообще**. Все соединения шли
сразу на IP-адреса, то есть имена резолвились где-то ещё. Причина — Private DNS: на
устройстве включён DoT (`xbox-dns.ru`), а `applyPrivateDnsBypass` выводил его сервер
мимо VPN. Отсюда два следствия, и второе — ровно то, на что жаловались:

- список посещённых доменов уходит провайдеру по тому самому каналу, от которого
  пользователь прячется, а адреса резолвятся по его геолокации, а не по узлу;
- резолвинг зависит от доступности сервера DoT на канале провайдера. Заблокировали
  или не доходит — имена не резолвятся ни у кого, при полностью живом туннеле.
  Снаружи это и выглядит как «VPN активен, а интернета в браузере нет».

Для прокси-транспортов обход не нужен: 853/tcp через прокси — обычное TCP-соединение,
tun2proxy его прокачает. Проверено до правки: DoT через узел отвечает за 407–490 мс,
TLS 1.3. Поэтому для VLESS Private DNS остаётся внутри туннеля — но только если узел
действительно пропускает 853/tcp. Проба делается один раз, до `establish`, ядро к тому
моменту уже поднято и проверено. Если узел не пропускает, обход возвращается: строгий
Private DNS без доступа к серверу убил бы резолвинг совсем.

После правки в логе туннеля видно и bootstrap (`10.1.11.1 -> 1.1.1.1:53`), и сам DoT
(`10.1.11.1 -> 111.88.96.55:853`), а браузер открывает страницы.

Для WARP/AWG поведение не менялось: там DNS идёт внутри WireGuard, и обход Private DNS
решает другую задачу.

### Открытое: UDP через узел не проходит

Побочная находка того же разбора: каждая UDP-сессия из браузера заканчивается
`timed out`. Инбаунд ядра ни при чём — SOCKS5 UDP ASSOCIATE принимается и отдаёт релей
на петле; не пропускает сам узел. Практическая цена невелика: браузер пробует QUIC,
не дожидается и открывает страницу по TCP.

Попытка закрыть QUIC маршрутом `udp:443 -> blackhole` в конфигурации Xray **не
помогает и откачена**: blackhole роняет пакет молча, tun2proxy об отказе не узнаёт и
всё равно выдерживает свой таймаут — замерено, поведение не изменилось. Быстрый отказ
надо делать в tun2proxy, из Kotlin до него не дотянуться.

## Подписка: потоковый импорт и автообновление

6 августа 2026. `VlessSubscriptionFetcher` наконец подключён к экрану импорта —
до этого он был написан, покрыт замерами и не вызывался ниоткуда, а импорт по URL шёл
через `readText()` всего тела. На агрегаторе из замеров выше это гарантированный OOM.

Проверено живой загрузкой (`HugeSubscriptionFetchProbe`, ходит в сеть, по умолчанию
пропускается):

| | было (`readText`) | стало (потоком) |
| --- | --- | --- |
| удержанная память | 347 МБ | 3 МБ |
| прочитано тела | всё | 101 КБ |
| время | 1 924 мс | 739 мс |
| шагов прогресса на экране | 0 | 17 |

Чтение обрывается на лимите профилей (`stoppedEarly`), поэтому тело и не скачивается
целиком. Диалог импорта показывает счётчик профилей и прочитанный объём: подписка
идёт десятками секунд, и без этого экран выглядел зависшим.

Обновление раз в N часов ставится `WorkManager` (`VlessSubscriptionWorker`), интервал
берётся из заголовка `profile-update-interval` подписки и зажимается в 1…168 часов.
Расписание восстанавливается на каждом запуске приложения: оно переживает
перезагрузку, но не переустановку.

### Что подписка вправе менять в списке

Три правила в `VlessSubscription.planSync`, и каждое стоит за конкретной ошибкой:

- **выжившие остаются на своих местах.** Перебор уже расставил их по
  работоспособности; пересортировка по порядку подписки вернула бы мёртвые записи
  наверх;
- **удаляются только те, что были в подписке и пропали.** Профили, добавленные
  вставкой из буфера, подписке не принадлежат;
- **первая загрузка не удаляет ничего.** Состава прошлой загрузки нет, и любой уже
  сохранённый профиль выглядел бы как пропавший.

Сравнение идёт по `VlessConfig.identity`, поэтому перенумерация узлов в имени —
обычное дело у провайдеров — не выглядит как удаление и добавление.

### Мина: подписка другого протокола выглядела как «не изменилась»

Первая версия решала, что тело не про VLESS, по числу локальных профилей. У
пользователя с уже импортированными профилями это число не ноль, и подписка AWG
молча получала ответ «не изменилась» вместо разбора. Решение принимает загрузка, а не
хранилище: пустой результат по незнакомому адресу — отдельный исход `NoVlessFound`, и
только он уводит тело в разбор AWG/WARP.

### Мина: `setMessage` съедает `setItems`

Состояние подписки, поставленное сообщением диалога, заняло место списка — меню
импорта пропало целиком, осталась одна «Отмена». Лечится `setCustomTitle`.

### Мина: перебор сдавался по таймеру там, где уходить некуда

Подключение останавливалось само примерно на восемнадцатой попытке из 252, и экран
показывал «НЕ ПОДКЛЮЧЕНО». Бюджет поиска (75 с) отдавал управление общей цепочке
WARP/AWG, а в режиме «импортированные конфигурации + протокол VLESS» обычный пул WARP
выключён: цикл честно доходил до «shortlist пуст» и гасил службу.

Бюджет времени осмыслен только там, где есть запасная цепочка. Без неё сдача по
таймеру означает не «попробуем другое», а «выключаемся на середине списка», поэтому в
режиме «только VLESS» перебор идёт по всему списку. Если список кончился, служба
останавливается сразу и с внятной причиной, а не через семь секунд бесполезной работы
общей цепочки.

Заодно бюджет одного узла уменьшен с 4 до 3 секунд: замеры на тестовом устройстве дают у живого
узла 320–550 мс, у мёртвого — весь бюджет. За те же 75 секунд теперь проходит 20
кандидатов вместо 18, а до рабочего узла на реальном списке дошло за 63 секунды.

## Встроенные WARP: счётчик уходил на чужую фазу

При выбранных встроенных WARP счётчик показывал «x/50», потом «x/4», и только через
полминуты начинался настоящий перебор. Воспроизведено на тестовом устройстве:

```
Пробуем MASQUE / HTTP3.
MASQUE кандидаты: 4 штуки
... четыре раза: failed to dial MASQUE QUIC: timeout: no recent network activity
MASQUE не дал стабильного трафика. Переходим к WireGuard fallback.   (+33 с)
DIAG attempt-ordinal: progressTotal=50 -> currentAttemptOrdinal=1
Пробуем endpoint: источник bundled-seed, режим warp-awg-exact
```

«x/4» — это фаза MASQUE. Подключение в итоге честно уходило на AWG из встроенного
списка (`bundled-seed`, `warp-awg-exact`), но полминуты каждого запуска съедал
транспорт, который на этой сети не поднимался ни разу: QUIC режется, и все четыре
кандидата падали по таймауту.

В «Авто» MASQUE идёт первым по догадке `hasStrongVerifiedMasque`, и тормоза у этой
догадки не было: серия срывов останавливала только **явно выбранный** MASQUE
(`EXPLICIT_CHOICE_FAILURE_LIMIT`), а в «Авто» cooldown требовал мобильную или
ограниченную сеть — на обычном Wi-Fi он не срабатывал никогда. Хуже того, сам
`hasStrongVerifiedMasque` вдобавок блокировал cooldown, то есть ровно то условие,
которое ставило MASQUE первым, мешало его оттуда убрать.

Теперь `AUTO_FIRST_FAILURE_LIMIT = 2` срыва подряд убирают MASQUE и с первого места, и
из цепочки целиком — оставленный в ней, он сжёг бы своё время просто позже. Порог ниже
явного (3) намеренно: в «Авто» MASQUE идёт по догадке, а не по просьбе пользователя.
Отсрочка временная, счётчик срывов протухает за десять минут.

Заодно фаза MASQUE публикует свою метку сразу, а не при ближайшем broadcast: пока
метка лежала до конца скана, экран несколько секунд считал фазу неизвестной и показывал
заглушку по размеру списка встроенных профилей — тот самый «x/50» перед «x/4».

Проверено на устройстве: третий цикл подряд пишет «MASQUE сорвался 2 раз подряд на этой
сети — в этом цикле его пропускаем», перебор стартует сразу с «1/50» по `bundled-seed`,
и подключение идёт `warp-awg-exact`.

## Ложные срабатывания смены сети

Признак «это та же подложная сеть» включал BSSID — MAC конкретной точки доступа. Он
меняется при каждом роуминге: в mesh-сети, с репитером, просто при переходе между 2.4
и 5 ГГц одной точки. Сеть при этом та же и маршрут наружу тот же, но подпись менялась,
служба видела смену сети и рвала туннель любого протокола на ровном месте.

Опора теперь такая: **SSID → шлюз по умолчанию → BSSID**. Шлюз одинаков для всех точек
одной сети, то есть переживает роуминг, в отличие от BSSID; сам BSSID остаётся
последней запасной опорой, когда нет ни имени сети, ни шлюза. Правило вынесено в
`NetworkIdentity` и проверяется unit-тестами, а не роумингом по квартире с телефоном в
руках.

Важная деталь для отладки: без разрешения на местоположение Android отдаёт
`<unknown ssid>` и `02:00:00:00:00:00` вместо настоящих значений. Nova таких разрешений
не просит, поэтому на большинстве устройств подпись и так опирается на шлюз — а BSSID
подставлялся ровно там, где система его всё-таки отдаёт.

## Определение страны выхода

Бейдж показывал «VLESS: RU» при выходе в Сингапуре. Причина та же, что у пинга и DNS,
и всплыла она в третий раз: **при раздельном туннелировании пакет Nova остаётся вне
VPN**, поэтому любой запрос «по маршруту по умолчанию» уходит мимо узла и приносит
адрес и страну провайдера.

Виноваты были обе стороны:

- экран для VLESS звал `fetchIpSnapshot(null)` — комментарий рядом честно объяснял,
  что для WARP так можно, «потому что Nova всегда внутри VPN». Для VLESS это неверно;
- служба для VLESS шла общим путём с запасным вариантом `fetchExitSnapshot(null)` —
  тем же выходом мимо узла.

Оба пути ведут теперь через SOCKS-инбаунд ядра. Замеры через живой узел объясняют
выбор источника:

| источник (через узел) | результат |
| --- | --- |
| `http://1.1.1.1/cdn-cgi/trace` | пустой ответ |
| `https://www.cloudflare.com/cdn-cgi/trace` | `loc=SG`, `colo=SIN` |
| `https://ipinfo.io/json` | `"country": "SG"` |

Простой HTTP на anycast-адрес резолвера через узел не проходит вовсе, поэтому берётся
HTTPS-трейс. Третья правка — прошлая страна больше не подставляется к новому адресу:
она годится только для того же IP, иначе смена узла давала новый адрес со старой
страной. Не знаем страну — показываем пустой, а не позапрошлую.

### Мина: бюджет пробы короче самого узла

После починки страны пропал пинг — на рабочем туннеле висело «Ping: ---». Проба в
сессии ждала 1800 мс, а живой сингапурский узел отвечает за 1974 мс: здоровье
подтверждалось другими признаками, а публиковать задержку было нечего.

Бюджет в сессии поднят до 4 с, а поиск живого узла больше не режет одну попытку
фиксированными двумя секундами — берёт весь остаток. Проверено, что дело в узле, а не
в пробе: TLS-рукопожатие через него занимает 1.4–1.9 с к любому хосту, так что
показанные ~1850 мс — честная задержка, а не артефакт измерения.

### Мина: снятая заметка подменялась копией из prefs

Заметка «Профиль 2/151 не ответил — берём следующий» оставалась на экране поверх
подключённого туннеля. `getLastTransportNotice` читала файл состояния и уходила в
`ifBlank` на prefs своего процесса. Но пустая строка в файле — это «служба сняла
заметку», а не «данных нет»: проверять надо наличие ключа, а не пустоту значения.

## Что осталось

1. Go-сторона: порт REALITY-клиента, Vision и XHTTP в `nova-core`, экспорт через
   gomobile, SOCKS5-inbound.
2. Kotlin-сторона: хранилище профилей (сейчас список ссылок в `vless_profiles.json`,
   потолок `MAX_VLESS_PROFILES` — для тысяч записей не годится, нужен Room), отдельный
   экран подписок (сейчас состояние показывается строкой в диалоге импорта), выбор
   протокола рядом с AWG/WARP. Профиль задаётся ещё и через adb:
   `am start -n com.brent.nova/com.example.nova.MainActivity -a SET_VLESS_PROFILE --es vless_link '<ссылка>'`.
   Внимание: в списке «Выбор протокола» кнопки VLESS нет, и открытый экран настроек
   показывает «AUTO», хотя сохранено `vless`. Пока нет кнопки, менять регион там при
   выбранном VLESS нельзя — выбор сбросится.
3. Проверка на устройствах: тестовое устройство и Redmi Pad 2 Pro (HyperOS 3).

## Побочная находка: стрип символов

Сборка `nova-core` шла без стрипа. С `-trimpath -ldflags="-s -w -buildid="` библиотека
уменьшается с 21.7 МБ до 15.5 МБ на ABI. В APK нативные библиотеки сжимаются
(`useLegacyPackaging = true`, `extractNativeLibs="true"`), поэтому итоговый размер APK
изменился мало — но распакованный размер на устройстве стал заметно меньше.

## Мина: `jniLibs` перекрывают `.aar`

`app/src/main/jniLibs/{arm64-v8a,armeabi-v7a}/libgojni.so` лежат в репозитории и имеют
**приоритет над `jni/` внутри `.aar`**. Из-за этого пересборка `.aar` не влияет на ARM:
в APK продолжала попадать июльская сборка, и только x86/x86_64 брались из `.aar`
(проверено по md5). Обе ARM-копии заменены; при любом изменении `nova-core` их нужно
обновлять вместе с `.aar`, иначе новый экспортированный метод даст `UnsatisfiedLinkError`
на всех реальных устройствах.

## Оценка размера при встраивании ядра

Первоначальная оценка «+120 МБ» исходила из несжатой упаковки. При текущих настройках
нативные библиотеки в APK сжимаются примерно в 2.3 раза, и x86/x86_64 можно отбросить
(`liboperaproxy.so` и `libtun2proxy.so` собраны только под две ARM-архитектуры). Это не
меняет вывод — разница между «портировать нужное» и «встроить ядро» остаётся на порядок,
— но реальная цена ниже первоначальной оценки.
