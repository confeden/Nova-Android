# Почему не проходит регистрация WARP: блокировка по SNI

Замеры сделаны 4 августа 2026 на Pixel 4a, домашний Wi-Fi и LTE MegaFon.

## Что видно снаружи

Приложение подолгу стоит на «ПОДКЛЮЧЕНИЕ… 1/50», в логе после «Подготовка к
подключению» тишина. Обычный интернет при этом работает.

## Диагноз

Блокируется не адрес и не DNS, а **имя в TLS ClientHello**. Проверка на одном и том же
IP, менялось только имя:

| Запрос | Результат |
| --- | --- |
| `https://www.cloudflare.com/` на 104.16.192.82 | **200** |
| `https://api.cloudflareclient.com/` на 104.16.192.82 | **000** — соединение обрывается |
| `http://104.16.192.82/` без TLS | 403 (Cloudflare отвечает, адрес живой) |

То есть IP доступен, TCP проходит, а рукопожатие с `api.cloudflareclient.com` в SNI
обрывается на DPI. Домен резолвится корректно: системный DNS телефона отдаёт
104.16.192.82, честный DoH — те же адреса Cloudflare.

Что **не** является причиной, хотя выглядит похоже:

- **Не DNS.** На ПК провайдерский резолвер возвращал 8.6.112.0 и 8.47.69.0, и это сбивает
  с толку. Но на телефоне DNS отдаёт настоящие адреса, а соединение всё равно рвётся.
- **Не блокировка Cloudflare целиком.** `www.cloudflare.com` и `1.1.1.1` открываются.
- **Не сотовый оператор.** По LTE MegaFon картина ровно та же — значит, фильтр не у
  одного провайдера.

Через живой туннель API отвечает нормально: `api.cloudflareclient.com/v0a4005/reg` даёт
405 (Method Not Allowed на GET — то есть запрос дошёл до Cloudflare).

## Что из этого следует для обхода

**Фронтинг не работает.** Запрос с SNI `www.cloudflare.com` и заголовком
`Host: api.cloudflareclient.com` Cloudflare отклоняет с 403 — межзонный фронтинг у них
закрыт давно. Этот путь можно не пробовать.

Рабочих направлений два:

1. **Спрятать SNI.** Cloudflare поддерживает ECH, а в `nova-core` уже есть
   `refraction-networking/utls`, который его умеет. Это правильное решение: DPI просто
   нечего будет сопоставлять. Цена — работа в Go-ядре и пересборка `.aar` вместе с
   `jniLibs` (см. предупреждение про приоритет jniLibs в `vless-reality-plan.md`).
2. **Регистрироваться через уже поднятый канал.** Это в Nova **уже реализовано**:
   `WarpClient.register` строит порядок профилей через `buildRegistrationProfiles`, и
   среди них есть путь через Opera-прокси, который поднимается сам и не зависит от
   Cloudflare. В наблюдаемом запуске сработал именно он: `anonymous registration` и
   `device registration` прошли с первой попытки, после чего WARP поднялся штатно.

## Что стоит улучшить

Обход срабатывает, но не сразу: до него дело доходит после ожидания на прямом пути, и
пользователь несколько минут смотрит на «1/50». Признак блокировки распознаётся дёшево —
TCP до адреса Cloudflare устанавливается, а TLS с нужным именем не завершается. Поймав
такую пару, разумно сразу переключаться на профиль через прокси, не досиживая таймаут.
